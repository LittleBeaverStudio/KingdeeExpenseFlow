### v2.1.1 向导改了什么（起因与取舍）

客户同一账套下多家都买了收票服务（如 101 示例科技 / 104 示例四科技），而发票云权益是**按税号**划分的
（官方原文：「请使用**税号对应的企业授权**，不要用租户授权！！」），每家各一组 `client_id / 购方税号`。
原设计让用户自己维护「组织名」+「对应金蝶组织」，界面繁琐（下拉框 + 新建组织弹窗 + 两行额外字段），
实测用起来很卡手。本次改动：

1. **向导「发票云」改成「一家一框」**：只填 `购方企业全称 / 购方税号 / client_id / client_secret` 四项，
   多家就「＋ 添加一家」。**删掉**「组织」下拉、「对应金蝶组织」字段、「新建组织」弹窗、「删除组织」按钮。
   **组织名自动 = 购方企业全称**（发票云的「组织」本来就是购方企业本身）。
2. **组织名自动匹配**：`upload` / `create-recvin` 的 `--org` 可留空 —— 脚本读报销单的组织名称
   （`bill_org_no()`），按「金蝶组织名 ↔ 购方企业全称」自动选中对应那家
   （`piazzone_client.select_org(org_name=…)`，支持简称/带后缀）。老的「对应金蝶组织」编码登记仍然兼容（按编码优先）。
3. 配了多家而两轮都没命中 → `errcode=ORGUNMATCHED`，**拒绝上传**（不猜、不拿别家授权硬跑）。
4. **修 bug**：向导里 `for k in pz_rows` 遍历的是 `(键,标签)` 元组，点「新建组织」/切组织时会抛
   `TypeError` 静默崩掉 —— 该分支已随本次重构删除。
5. `--check` 现在逐条列出「公司 ｜ 金蝶组织 ｜ 税号」，便于核对路由。
6. **观感与可用性**：主题换 `clam` + 扁平化配色（原来是系统默认皮、像 Win98）；**一家一个卡片框**
   （浅底 `#f8fafc` + 1px 边框）；**整窗不用任何分隔线** —— 区块之间靠留白分区、页脚靠窗体底色（灰）自然断开；
   每张卡片**右上角一对小按钮「＋ / －」**：＋ 加一家、－ 删这张（只剩一家时「－」置灰防误删）；
   页脚只留右对齐的「保存 / 取消」；内容区**可滚动**、页脚固定 ——
   修掉了"公司加多了窗口顶出屏幕、`保存` 按钮看不见"的问题。

## 二、`ValidateFlag` 越狱是怎么发生的（机制，不是漏洞）

金蝶 WebAPI `Save` 的官方参数 `ValidateFlag`（官方原文：「设为 false 时不对数据合法性进行校验」）
是一个**总开关**：置 `false` 时**整批业务校验被跳过**，而「发票金额不允许小于报销金额！」正属于这批校验。
本 skill 的 `save()` 为了能写字段（否则会被必填项卡住）默认传 `false`
→ 于是**同一张 0 发票的差旅报销单**：

| 报文 | 结果 |
|---|---|
| `ValidateFlag=true` | ❌ `MsgCode=11`，Errors 含「发票金额不允许小于报销金额！」 |
| `ValidateFlag=false` | ✅ `IsSuccess=true`，生成单号，**`Submit` 也能到 `B` 审核中** |

⇒ **不是攻破了什么，而是金蝶把"关掉校验"的开关摆在了 API 参数里。**
UI 走强校验、API 可关，两者授权不同步，这中间的差就是"越狱"。

### 闸门自身验证记录（2026-09-22，全打桩、零成本，不会真提交）

```python
orig = kd._svc
def trap(m, f, d, timeout=90):
    if m == "Submit":
        raise AssertionError("❌ 闸门失效：已发出 Submit 请求")
    return orig(m, f, d, timeout)          # 严格探针的 Save 走真实调用
kd._svc = trap
ok, st = kd.submit(fid, formid)            # 期望 ok=False, MsgCode="GUARD"，Submit 从未被调用
```

| 场景 | 结果 |
|---|---|
| 收票 **0 行** + 报销金额 > 0 | ✅ block，`submit` 返回 `MsgCode=GUARD`，**`_svc` 全程未被调用**（没发 Submit） |
| 挂了票、金额也对齐，但**票无发票云流水号** | ✅ block（"等于没上传发票"），同样不发起 Submit |
| 票有流水号但**跨组织**（票属 104 / 单属 101） | ✅ block，话术点明"提交成功也会被驳回为 D" |
| 发票 800 < 报销 1000（金额未对齐） | ✅ block，提示用 `expense_edit.py fit` 调低 |
| 同组织 + 有流水号 + 金额对齐（**对照组**） | ✅ `blocks = 0`，正常放行 |
| `link()` 挂「无流水号」票 | ✅ 在 **Save 之前**中止，**没有写库** |

### 判据 4（金蝶严格校验）的盲区

`strict_probe` 靠 `Save` 报文触发，**会被"编辑锁冲突"打断**：报 `MsgCode=4`
「XXX使用业务单据…冲突，请稍候再使用」，此时 `errors` 里**根本没有发票金额那一句**
→ `strict_errors` 为空 → 该道判据**静默放行**。实测重试 2 次仍冲突
（**同一账号"先 View 再 Save 探针"会自锁**）。
⇒ 所以判据 5（skill 自算）是**主力**，判据 4 只是"金蝶视角的加分证据"。**拿不到金蝶结论时，更要自己算。**

### 闸门的边界（别过度承诺）

- 闸门**只管"发票金额 / 发票来源"这一类风险**，**不管单据完整性**（必填项是否填全）。
  `strict_probe` 顺带发现的必填缺失只作提示打印，不阻断 —— 因为 `Submit` 本来就不校验必填。
- 闸门在**库与 CLI 两层**都生效（`submit()` 无条件跑、`link()` 无条件跑），且**没有参数可绕**；
  但**源码级绕过路径始终存在**：调用方直接 `kd._svc("Submit", ...)` 就跳过了。
  闸门防的是"**误用默认参数**"和"**图省事的越狱**"，不是"**恶意改代码**"。

## 三、金额：勾稽关系与方向不对称

### 勾稽关系（2026-09-22 实测，101731 六行 + 101464 十二行逐行吻合）

```
含税 ExpenseAmount  =  不含税 TaxSubmitAmt  +  税额 TaxAmt
                    =  LOCNOTAXAMOUNT（不含税）
                    =  FTravelAmount（差旅费金额，差旅单专有）
                    =  ExpSubmitAmount / LocExpSubmitAmount
```

| View 键 | Save 键 | 含义 | 实测（101731 行1） |
|---|---|---|---|
| `ExpenseAmount` | `FExpenseAmount` | **含税**（价税合计） | 234.0 |
| `TaxAmt` | `FTaxAmt` | 税额 | 19.32 |
| `TaxSubmitAmt` | `FTaxSubmitAmt` | **不含税**（名字反着起的，别被"Submit"骗） | 214.68 = 234 − 19.32 |
| `LOCNOTAXAMOUNT` | `FLOCNOTAXAMOUNT` | **不含税** | 214.68 |
| `FTravelAmount` | `FTravelAmount` | **差价旅费金额 = 含税**（差旅单必写） | 234.0 |

> ⚠️ 差旅费金额的键是 **`FTravelAmount`**，不是 `FExpTravelAmount`（旧文档写错，已订正）。

### 方向不对称（2026-09-22 实测）

| 方向 | 结果 | 依据 |
|---|---|---|
| **调低**（报销 2474.76 → 发票 1606.76） | ✅ 安全，不会踩校验 | 101464 dry-run |
| **调高**（在报销单上加钱） | ❌ 被拦：**「关联费用申请金额超出源单已下推报销金额！」** | 实测 101464 / 101404 写入失败 |

→ 想"多报"只能**回出差申请单加额度**，别在报销单上加。所以 `fit` 对"目标 > 发票合计"
（有票时）或"无票时目标 > 当前额"一律**硬拒**。

### 报销金额 vs 申请金额（2026-10-10 口径）

**报销金额可以大于申请金额，业务上没问题** → 不要硬拦截，提醒用户即可。
实测：申请 10.00 的单，把报销额改到 43.72（= 两张发票合计），`set-detail` 写入成功、
`strict`（ValidateFlag=true）也通过；金蝶把源单的 `FPushReimbAmount`（已下推报销金额）反写为 43.72，
并把申请单自动关闭（`FCloseStatus` A→B）。
⚠️ 「关联费用申请金额超出源单已下推报销金额」这条限制**只在「下推」时校验、保存报销单时不校验**
→ 所以直接改明细金额能绕过它；但改完要回看源单反写值是否已超申请额，超了就**告知用户**。

### `Save` 成功会把「暂存(Z)」推进成「已提交(A)」（2026-09-22 实测）

| 单据 | 我的写入 | 写入后状态 |
|---|---|---|
| `101401` | ✅ **成功** | **Z → A**（并分配单号 `CLFBX00000001`） |
| `101464` | ❌ 失败（反写超限） | 仍 `Z` |
| `101404` | ❌ 失败（反写超限） | 仍 `Z` |

⇒ 差别就在**写入成功与否**。`set_detail` / `fit` 虽然只改金额，但会把单据**推进状态**，
而 `A` 之后 **WebAPI 撤不回**（`UnSubmit` 不存在、`UnAudit` 报"已关联工作流实例"）。

## 四、本账套「发票金额 ≥ 报销金额」强校验的真实情况

2026-09-22 全量实测（**推翻旧结论**）：取 1129 张报销单（费用 828 + 差旅 301）逐单核对，
**712 张**存在「已挂发票 < 报销金额」，其中大量为「报销十几万 / 收票 0 行 / 状态 C 已审核」。
View 直读子表逐单确认（非链接表推断）：

| FID | 单号 | 组织 | 状态 | 报销金额 | 收票行数 |
|---|---|---|---|---|---|
| 100147 | FYBX20240607000002 | 101 | **C** | 139,824.65 | **0** |
| 100130 | FYBX20240606000004 | 101 | **C** | 86,400.00 | **0** |
| 100116 | FYBX20240604000008 | 104 | **C** | 68,786.00 | **0** |
| 100105 | FYBX20240531000001 | 101 | **C** | 13,211.00 | **0** |

→ **一张发票都没有，也能保存、提交、审核通过到 `C`。**
所以「昨天没传发票也提交到审核人」是**系统本来就不拦**，不是"校验被绕过"。
⚠️ 别再写「校验发生在审核环节」—— 审核环节同样不拦（上面 4 张都是 C）。

🔴 **`Submit` 永远返回 `IsSuccess=true`**：WebAPI 提交不校验金额、不跑 UI 表单插件。
**"提交成功" ≠ "校验通过"**，不要拿 `Submit` 的返回值当金额合规的证据。

## 五、发票来源：手工建票 vs 发票云采集

### 流水号只在「采集那一刻」产生（2026-09-22 实测）

| 上传方式 | 结果 |
|---|---|
| 发票云 **手机小程序**上传 | ❌ 后台**依然没有**流水号 |
| 把 PDF 传到收票单**附件** | ❌ 流水号仍为空（传完等 25s 仍空） |
| **手工建收票单 → 挂到同组织报销单** | ❌ **不会补号**（事后从电子税务局重新下载，仍无流水号） |
| **员工在报销软件里上传**（走一次流程） | ✅ **有流水号**（钱八 24 张 100% 有号，`GEN='3'`） |
| 管理员在**金蝶云星空里点「下载」**（电子税务局来源） | ✅ 有流水号（归集账号 `16394` 建的票 100% 有号） |

### 手工建票丢掉的是「三重财务保护」，不只是流水号

| 保护 | 发票云采集的票 | 手工建的票 |
|---|---|---|
| **防重复报销** | 发票云按 `expenseStatus`（1未用/30在用/60已用）锁票，一张票只能用一次 | ❌ **完全没有** —— 且金蝶**不校验发票号重复**（实测同号能建第二张），同一张票可被建两次、报两次 |
| **票据数据可信** | 税局原始数据回写（金额/税号/票号不会错） | ⚠️ 靠 agent 从 PDF/图片 OCR 提取 → 错一位数就挂错票 |
| **验真与状态** | `ISEXAMINE=1`（已查验）、PDF/XML 原件留存 | ❌ `ISEXAMINE=0`，无查验记录、无原件 URL |

⇒ **从"单据能不能提交"看，流水号确实不重要；从"财务内控"看，丢的是防重、可信、验真三件事。**

字段级对照：

| 字段 | 手工建 | 自动归集（对照） |
|---|---|---|
| `GENERATETYPE` | `' '`（空） | `3` |
| `FPIAOZONESERIALNUMBER` | **`' '`（空）** | `7d3d30bd…`（33 位） |
| `PDFURL` / `PICTUREURL` / `PICTUREXMLURL` | **全空** | 全有（`api.piaozone.com`） |
| `ISEXAMINE` | `'0'` | `'1'` |

⚠️ 手工建的票**还会占用发票号码**（本环境池里发票号基本无重复），可能干扰后续自动归集。
**测完记得删**（员工账号无删除权限，须用有权限账号）。

### `--bill-fid` 为什么必填

发票云要求 `bxd_key`（报销单ID）非空；真实流程这一步本来就发生在报销单上（界面「选择发票」），
所以**先有报销单才能上传**。`upload` 只能拿到流水号（发票云侧成立），但**金蝶收票池不会因此生成收票单**，
收票单必须由 `create-recvin`（或界面「发票导入单据」）来建 —— "只上传不建票"不够。

### 三条路线取舍（2026-09-22 实测后重排）

| 维度 | **路线1：中央 agent + 服务账号**（⭐ 推荐） | **路线2：员工端 + 精准数据规则** | **路线3：员工端用服务账号**（❌ 已否决） |
|---|---|---|---|
| agent 跑在哪 | **一处**（你的机器 / 公司服务器） | 每个员工自己的电脑 | 每个员工自己的电脑 |
| 高权限凭证放哪 | **只存一处，绝不下发** | 员工**自己的**账号（低权限） | ⚠️ 服务账号被复制到 N 台 = **全公司都拿到管理员账号** |
| 员工前端能看到池票 | ❌ 看不到（数据规则**不动**） | ✅ 能看到「自己 + 归集账号」的票 | ✅ 全都能看到 |
| 员工能看到同事私有票 | ❌ 看不到 | ❌ 看不到（规则里排除掉） | ✅ 全都看得到 |
| 抢票风险 | 无（agent 按发票号精确匹配 + 查重） | ⚠️ 有（池票无归属标注，两人可挂同一张） | ⚠️ 高 |
| 员工操作次数 | **0 次**（v2.1.0 起 agent 服务端上传建票） | 1~2 次（还要自己进金蝶选票） | 1 次 |

> **必须说清的技术硬事实**：金蝶的**数据规则对 UI 和 WebAPI 一视同仁** ——
> 实测钱八用 WebAPI 能 `View` 打开**同事的**收票单（84 个字段全返回）、能查到 18 个制单人的票。
> 所以**同一个账号，不存在"agent 能看、前端看不了"**。要同时满足「智能体取得到票」+
> 「员工前端看不到池子」，只有两条真出路：① 身份分离（路线1）；② 系统层面禁止该账号网页登录。

### 收票池可见性：按「来源组织」切，不是按制单人（2026-09-22 三组对照）

| 账号 / 状态 | 可见收票单 | 判定 |
|---|---|---|
| 取数账号 `13800000000` | **2000 张 / 23 个制单人 / 组织 101+104+105** | 全池 |
| 员工钱八 `598079`（**改权限前**，勾着"只能查看自己单据"） | **24 张 = 她自己的** | 仅自己 |
| 员工钱八 `598079`（**关掉"只能查看自己单据"后**） | **2000 张 / 18 个制单人 / 组织 101 全可见** | ⚠️ **整组织可见**，同事私有票也露出来 |

**判别字段是 `FSOURCEORGID`（来源组织）**：同一位制单人（`16394`）建的单 ——
组织 101 的 `SPD00008766/08767/08768/08769/08770`（即那 5 张"缺票"）钱八 **5/5 可见**；
组织 104 的 `SPD00008771/08772/08773` **不可见**。

- ⚠️ **代价**："把'只能查看自己单据'关掉" ≠ "只多看到归集票"，而是**把同组织同事的票全放出来**
  （样本 6/6 可见，且能 `View` 打开同事的单、84 个字段全暴露）→ **不满足"前端看不到别人的票"**。
- ✅ **报销单没有被连带放开**：钱八仍只看得到自己的 2 张差旅单，`View` 别人的单报
  `MsgCode=11`「您没有单据编号为…的差旅费报销单的权限！」

复现命令（`helpers/perm_probe.py`，**纯只读**）：

```bash
python helpers/perm_probe.py --pool --bills --by-invoice 24000000000000000001
```

### 权限配置的三个层次（只在 UI 能做，WebAPI 读不到）

> 前提：金蝶的权限体系 WebAPI **不可读**（实测 `SEC_Role` 报"业务对象不存在"，
> `SEC_User` / `SEC_DataRule` 报"**您没有…的查看权限**"），所以 agent 无法代劳。

| 层 | 位置 | 控制什么 |
|---|---|---|
| 1. **功能权限** | 角色 → 业务对象 → 功能权限 | 能不能**打开**收票单（查询 + 查看给"是"） |
| 2. **数据权限（数据规则）** | 角色 → 基础资料权限 → 数据规则 | 能看到**哪些行**（「只能查看自己单据」在这里改） |
| 3. **字段权限** | 同页的列 | 能看到**哪些列**（建议隐藏金额/税号） |

**精确做法：新增一个角色，别改现有角色**（金蝶多角色权限取并集，加法最安全、可回退）：

1. 新建角色 `发票池-只读`；功能权限只给 **查询 + 查看**。
2. 基础资料权限里给收票单挂数据规则：`FCreatorId = <归集账号内码，如 16394>`
   （若版本支持"或"，写成 `FCreatorId = 16394 或者 FCreatorId = 当前用户`）。
3. 把该角色**追加**给员工（员工原有角色不动）。
4. 净效果：员工可见 = **自己建的票** ∪ **归集账号建的票**。

**走这条路之前先想清楚 3 个坑**：
1. **池票没有"归属"标注** —— 归集账号建的 635 张票，系统里没有字段说明哪张属于哪个员工，员工只能靠发票号搜。
2. **票会被抢** —— 两人都能看到同一张票、都能挂；金蝶不校验发票号重复 → 财务必须人工查重。
3. **仍然没省掉一次操作** —— 员工还是要自己进金蝶选票。

## 六、跨组织报销：三轮结论修正过程

**问题**：能不能把 A 组织的发票挂到 B 组织的报销单上？

**结论：不能。而且是"能写进去、单据却不可用"的那种不能。**

实测三轮，结论逐轮修正（留档，避免再走回头路）：

| 轮次 | 看到的现象 | 当时的错误结论 |
|---|---|---|
| ① | `Save` 写 `FRecInvInfo` 成功、收票单联动回写 | "能挂" |
| ② | `Submit` 也成功，当场读到 `B` | "接口完全接受" |
| ③ | 随后变 `D`；**界面点「查看发票」直接报错** | ✅ **真结论：不可用** |

**界面上真实报的错**：
```
驳回：无法获取当前关联收票单的发票云发票流水号，请尝试删除收票单后重做收票
```

**为什么能写进去 —— 走的是官方没提供的那条路，不是"绕过后门"**：

1. 金蝶 WebAPI 根本没有"补发票"这个 Operation（`ER_ExpReimbursement` 的 18 个里没有）。
   发票云取票 + 回写流水号是**纯 UI 交互**。
2. 所以 WebAPI 挂票只能**直接 Save `FRecInvInfo` 子表** —— 等于写一行"指向某张收票单"的关联记录，
   **完全跳过发票云的取票与组织归属校验**。
3. 我们的 `Save` 报文还额外把校验关掉了：`ValidateFlag=false` + `IsVerifyBaseDataField=false`。
4. 于是校验被**推迟到界面打开 / 审核环节**才发生 → 表现就是
   「Save ✅ → Submit ✅（B）→ 界面/审核 ❌ → `D`」。

本次两张单各踩了不同的坑，正好把三条硬约束都验证到：

| 报销单 | 组织 | 收票单 | 组织归属 | 发票云流水号 | 实际报错 |
|---|---|---|---|---|---|
| 100005 | 104 | SPD00000002 | ❌ 属 101 | ❌ **空**（非发票云归集） | 「无法获取…发票云发票流水号」 |
| 100006 | 105 | SPD00000001 | ❌ 属 101 | ✅ 有（`GENERATETYPE=4`） | 「【收票服务】许可已过期失效 [0300]」 |

→ 两张单的失败**都可以归到"票不是本组织的"**；第 3 条（105 许可过期）是**叠加**上去的独立故障。

### 挂票会改写收票单（撤销时要还原）

收票单有 `SOURCEORGID`（来源/购方组织）与 `SETTLEORGID`（结算组织）。挂票后
`SETTLEORGID` 会被**改成目标报销单的组织**，同时 `LINKBILLID/LINKIVNUMBER/LINKBILLTYPE` 回写：

| 收票单 | SOURCEORGID / PURNAME | SETTLEORGID 原 | 被挂后 | LINK 字段 |
|---|---|---|---|---|
| SPD00000002 | 101 / 示例科技有限公司 | 101 | **104** | → 100005 / FYBX…0001 |
| SPD00000001 | 101 / 示例科技有限公司 | 101 | **105** | → 100006 / FYBX…0002 |

→ **挂错了要还原：`SETTLEORGID` 改回原组织 + 清掉 LINK 三件套**，否则这张票在原组织的收票核算里也是错的。

### `D` 的真正成因（不是"人工审批不通过"）

- `Submit` 返回成功，当场读到的状态 = `B`（审核中），收票信息保持 ✅；随后再读变 **`D`**，
  `APPROVERID` / `APPROVEDATE` 为空。
- **`D` = 「审核驳回」**（金蝶官方《单据状态通用说明》）：类同「创建」，可修改/删除/再次提交，
  但不可下推、不被其他单据引用。
- ⚠️ 触发点要写准：**报错不在"审核"动作里，而是在「单据被驳回后、在收票信息页签重新上传/补发票」时**。
  也就是说 —— 只要界面要按**本组织税号**去发票云取这张票（打开发票、补发票、重新上传、后续审核/结算），
  都会取不到。金蝶把"操作被拒绝"写作"驳回"，所以 `APPROVERID` 一直是空的 —— **根本没有审批人参与**。
- **全环境基线**（取 300 张报销单）：`C`×297、`B`×1（100009 长期卡住）、`D`×2（正是本次跨组织的
  100005 / 100006）→ **跨组织挂票是本环境唯一出现 `D` 的单**。
- 提示原文/流程节点**只在 UI 里看得到，WebAPI 读不到**（`WF_*` / `BOS_OperationLog` 等表单均不存在）。
  遇到 `D` **必须让用户去 UI 看提示原文**，不要自行重提交、更不要靠重试硬撞。

### 「没有购买发票模块」≠ 收票信息不可用

示例二科技（org 105）据称未购买发票模块，但收票信息写入成功（1 行）、提交 A→B 也成功；
收票单在 `CreateOrgId` = 0/101/104/105 下均可见。反向证据：org 105 名下
（`SOURCEORGID=105`）有 **701 张**收票单，`SETTLEORGID=105` 的有 542 张。

**正确理解**：发票模块影响的是**发票自动归集**，不是报销单「收票信息」子表本身。

### 为什么「示例二科技走附件」是对的 —— 是业务做法，不是系统限制

| 报销单 | 组织 | 状态 | 收票信息行数 |
|---|---|---|---|
| 历史单A (100007) | **105 示例二科技** | C 已审核 | **0 行** |
| 历史单B (100009) | 104 示例四科技 | B 审核中 | 1 行 |
| FYBX20260101000002 (100004) | 101 示例科技 | C 已审核 | 2 行 |

→ org 105 的历史报销单根本不用收票信息。**技术层面「能挂」≠ 业务层面「该挂」**；
skill 的默认动作是**先查该组织历史报销单用不用收票信息**，再决定走「收票信息」还是「附件」。

### 「收票信息为空」不是阻断项（已降级为 warn）

曾把它列为 blocks，理由是"大概率报发票金额不允许小于报销金额"——**实测推翻**：
`100007`（org 105）报销金额大于 0、收票信息 0 行，照样 Submit 成功并走到 `C` 已审核。
若仍按 blocks 处理，会把 org 105 这类"走附件"的正常单据误拦。

### 两条复核项

1. **同一张发票不要既挂「收票信息」又传「附件」**（100006 就是这样）：两个入口都会被财务看到，
   口径上算**重复佐证**，应二选一。默认：能挂收票信息就只挂；只有该组织既有做法是走附件才走附件。
2. **收票单上的联查号可能是「悬空号」**：`SPD00000002` 的 `FLINKIVNUMBER = CLFBX00000001`，
   但该差旅报销单**已不存在**（某次下推占号后未保存/被删）。
   → 挂票前若看到 `FLINKIVNUMBER` 有值，**先按单号反查该单是否真的存在**，别当成"已被用掉"而误判。
   （反查用 `ExecuteBillQuery` + `FBillNo='...'` 精确匹配，返回 `[]` 就是不存在，不会报错。）

## 七、其他实测细节

### 已评估否决：`LoginByAppSecret`（第三方系统登录授权）

| 否决理由 | 说明 |
|---|---|
| **落地成本高于收益** | 金蝶侧「集成用户」要额外建账号 + 后台配授权 + 可能还要白名单，用户明确表示"不现实、没有多余账号" |
| **会让 skill 出现两个登录口** | 一旦支持 `app_id`，就有两套配置键、两条登录路径 → **登录口必须只有一个** |
| 未实测 | 该分支当时照官方文档写的，本环境没有 AppID 可验 |

⇒ v2.0.11 起只有一条登录路径（`AUTH_SUFFIX` / `ValidateUser`），
`app_id` / `app_secret` / `KINGDEE_APP_ID` / `KINGDEE_APP_SECRET` 全部移除。

### 「同组织 + 无流水号」这个格子：业务校验层面能通（推翻旧推断）

拿手工建的收票单（`SPD00008775`，`GENERATETYPE=' '`、流水号空、`SOURCEORGID`=101）挂到**同组织 101** 的
差旅报销单，明细金额对齐后跑 `recvin_link.py strict <FID>`（= `ValidateFlag=true` 的真实业务校验）：

| 校验项 | 结果 |
|---|---|
| 「发票金额不允许小于报销金额！」 | 金额对齐后 **消失**（金额没对齐时会报 —— 这是**唯一**与发票相关的校验） |
| 「发票云流水号」相关报错 | **完全没有**（`Save` 阶段根本不查流水号） |
| 剩余报错 | 只有必填/勾稽类（`差旅费类型` 必录、`差旅费金额 ≠ 税额 + 费用金额`），与发票无关 |

→ **流水号不是业务校验项**：`Save` 不校验它，`Submit` 永远回 `IsSuccess=true`。
「无流水号致 D」的案例全部同时是**跨组织**的 → 真正致 D 的是**跨组织**，不是流水号。
（但流水号仍然是防重复报销的锚点，所以 v2.0.11 起仍作为硬闸门 —— 这是**内控要求**，不是系统校验。）

### 手工建票不校验发票号重复（会污染收票池）

拿一张**发票云里已有**（`SPD00008770`，发票号 `24000000000000000001`）的票号去手工新建，
`Save` 照样 `IsSuccess=true` 生成 `SPD00008787`，池里出现**两条同号记录**（一条有流水号、一条没有）。
→ 手工建票前**必须先查重**（`find --invoice-no`，且要用有权限账号）；**测完立即删**。

### 单据一旦 `Submit` 进审批流，WebAPI 就删不掉/撤不回了

| 尝试 | 结果 |
|---|---|
| `Delete`（状态 B） | ❌「只能删除创建，暂存，重新审核状态的数据!」（只放 `Z`/`A`/`D`） |
| `UnSubmit` | ❌ 无此服务，返回非 JSON（`JSONDecodeError`） |
| `UnAudit` | ❌「已关联工作流实例，不支持通过 WebAPI 接口进行传统审批」 |

→ **`ValidateFlag=false` 越狱提交是不可逆的**：单子进流程后只能人工在 UI 驳回/撤销。
所以「用测试单验证」前要清楚：**测试单基本收不回来**，别在正式账套里随便 Submit。

### 自动归集是「逐票同步」，不是整批投放

同一天（09-20）开的 3 张住宿专票，2 张已自动归集、1 张没有；曹操出行（吉利优行）的**普票**历史上能自动归集
（SPD00008225）→ 说明**不是"网约车票/普票不能归集"**。开票越久越可能已到位（08-31 的 8 张铁路客票全部到位）。
⚠️ 排查"查不到"时，第一步永远是换有权限的账号重查，确认真的没归集，再谈"归集进度"。

### 编辑锁与网络抖动

- **编辑锁冲突**（"…业务操作-[费用报销单-FYBX…-修改]冲突，请稍候再使用。"）是瞬时的，重试即可：
  实测同一脚本内重试 1 次即成功（`recvin_link.py` 已内置自动重试）。
  旧笔记写的"需客户端关闭或重下推新单"**是过度结论，别照做**。
- **出口代理会偶发瞬时故障**：形态为 `URLError: Tunnel connection failed: 502 Bad Gateway` 或
  `URLError: _ssl.c:1015: The handshake operation timed out`，实战中**连错 4 次第 5 次成功**。
  旧版 `_post` 没有重试，会把网络抖动误报成业务失败 → 已修：默认**重试 5 次 / 间隔 6s**。

### 发票云域名（2026-10-10 定论）

`base_url` 用 **`api.piaozone.com`** —— 唯一正确域名。早前写的 `api.piazzone.com`（**两个 z**）**该域名不存在**，
表现为 TLS 被重置，曾被误判成"需要 hosts 绑定 / 要 IT 放行"；**改对域名即可，不要再配 hosts**（配了反而更难排查）。
